## HTTP 链路

真实 HTTP 请求使用合成账号和合成岗位/简历文本：

1. `POST /api/auth/register` 注册学生与 HR。
2. `POST /api/auth/login` 获取学生与 HR Bearer token。
3. `POST /api/hr/jobs` 创建 HR 岗位草稿。
4. `PATCH /api/hr/jobs/{id}/status` 发布岗位。
5. `POST /api/student/resumes` 创建带 `sourceText` 的学生简历草稿。
6. `PATCH /api/student/resumes/{id}/status` 发布简历。
7. `POST /api/student/applications` 投递岗位。
8. `POST /api/student/matches` 生成规则匹配。
9. `GET /api/hr/applications?jobId={id}` 查询 HR 所属岗位投递。

第一次 HTTP 脚本误读登录响应字段为 `token`，导致岗位创建收到 `Bearer 令牌格式不正确`；实际 DTO 字段是 `accessToken`。修正后链路通过，摘要如下：

```json
{
  "jobId": 1,
  "resumeId": 1,
  "applicationId": 1,
  "matchScore": 75.0,
  "matchModel": "local-skill-coverage-v1",
  "hrApplicationCount": 1,
  "sourceTextRoundTrip": true
}
```

数据库复核：

```sql
SELECT COUNT(*) AS users_count FROM platform_user;
SELECT COUNT(*) AS jobs_count FROM job_posting;
SELECT COUNT(*) AS resumes_count FROM resume;
SELECT COUNT(*) AS applications_count FROM job_application;
SELECT id, resume_id, job_id, score, model_name FROM ai_match_result;
```

结果：

| 项 | 值 |
| --- | --- |
| `platform_user` | 4 |
| `job_posting` | 1 |
| `resume` | 1 |
| `job_application` | 1 |
| `ai_match_result` | `id=1`、`resume_id=1`、`job_id=1`、`score=75.00`、`model_name=local-skill-coverage-v1` |

`platform_user` 为 4 是因为字段名修正前的第一轮学生/HR 注册已经真实写入隔离库；这不影响后续链路，但记录为执行痕迹，避免把隔离库行数说成只有最终链路账号。
